## Règles transversales (toutes les étapes)

- **Fins de ligne : mesure par OCTETS avec Python** (`open(p,'rb').read().count(b'\r\n')`), JAMAIS avec `grep -c $'\r'` (faux positifs). Mesure faite le 21/10 : les fichiers de `web/src` et `web/tests` sont en **LF** (0 CRLF). Un nouveau fichier prend la fin de ligne de ses voisins (LF). Le hook refuse d'écraser un fichier à fins de ligne mixtes.
- Le dossier de travail contient des modifications NON COMMITÉES d'un autre lot (« mot de passe »), à ne pas toucher, ni défaire, ni commiter : `actions/admin.ts` (unlockPassword), `actions/auth.ts`, `lib/security-log.ts`, `lib/sliding-window.ts`, `lib/supabase/server.ts`, `lib/session-cookies.ts`, `lib/admin-data.ts`, `app/[locale]/admin/page.tsx`, messages fr/en/ar (clés `login.password`, `account.security`, `admin.locked`). Aucun agent ne commite, ne pousse, ne déploie.
- Français irréprochable avec accents, jamais de tiret cadratin, espace insécable U+00A0 avant `:` `;` `?` `!` dans les textes visibles français. TypeScript strict, aucun `any` ni `as` évitable, types de retour sur les exports, `type` plutôt qu'`interface`, `const` objects plutôt que `enum`. Aucun secret, aucune adresse e-mail ni jeton dans les journaux ni dans l'état retourné ni dans une redirection.

## Risques et parades (à tester)

1. E-mail jamais avant l'échec de la base : RPC → attendre → valider la forme du jeton (43 caractères `[A-Za-z0-9_-]`) → envoyer. Pas de `Promise.all`. Échec d'envoi = `mail_failed` ; réinviter renouvelle le jeton (ON CONFLICT).
2. Double envoi : plafond 1 envoi/minute par couple (campagne, adresse canonique) AVANT la RPC, déduplication du lot, bouton désactivé en cours.
3. Énumération de comptes : statut et e-mail identiques que le compte existe ou non ; sur `/i/` un refus unique pour jeton inconnu/expiré/utilisé/campagne close, un message neutre pour les conflits (55000, 22023).
4. `findUserId ?? createUser` AVANT la décision de la base = fabrique de comptes : pré-contrôle applicatif (`assignableRoles`) avant tout effet de bord ; la base reste l'autorité.
5. Faute de frappe sur l'adresse d'un membre = rôle donné à un tiers : double saisie de l'adresse (la vraie parade serait une migration `inviter_membre` avec jeton : DÉCISION D'AMINE, non faite).
6. Rejeu de jeton : `accepter_invitation` verrouille (FOR UPDATE) ; consultation GET ne consomme rien, seul le POST du bouton consomme.
7. Session existante d'une autre adresse sur `/i/` : refuser `other_session`.
8. Message libre : refuser `https?://`, `www.`, caractères bidi U+202A à U+202E et U+2066 à U+2069 et contrôles (sauf `\n`) ; précédé d'un titre fixe ; pas de texte libre dans le sujet (nom d'organisation seul, `[\r\n]` retirés) ; lien construit depuis `process.env.SITE_URL`, jamais depuis `Host`.
9. Jeton jamais journalisé, jamais dans l'état retourné ni dans une redirection (redirection constante `/mon-compte`).
10. Compte créé puis acceptation refusée : ordre `consulter_invitation` → `findUserId ?? createUser` → `accepter_invitation`.
11. Session non ouverte après acceptation : statut `signin_required` + lien `/connexion`.
12. Débit Resend : envois séquentiels espacés de 500 ms ; 429 = `mail_failed`.
